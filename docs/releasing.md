# Releasing engmech

Releases are published from GitHub Actions by pushing a version tag. The
[release workflow](../.github/workflows/release.yml):

1. builds the sdist and wheel once, checks that the tag matches the version
   built, and checks the package metadata (`twine check --strict`);
2. installs that wheel into a clean environment on Linux, macOS and Windows
   (Python 3.11 and 3.14), then runs the test suite and `engmech validate`
   against it;
3. publishes to [PyPI](https://pypi.org/project/engmech/) with Trusted
   Publishing, so no API token is stored anywhere;
4. creates the GitHub release, with notes generated from the merged pull
   requests, the distributions, and the validation report from each
   platform.

Nothing is published unless every step before it passes.

## One-time setup

Do this once, before the first release.

**PyPI.** Sign in at pypi.org, open *Your account → Publishing* and add a
pending publisher (it becomes a normal trusted publisher after the first
upload):

| Field | Value |
|---|---|
| PyPI project name | `engmech` |
| Owner | `davidson-engineering` |
| Repository name | `engineering-mechanics` |
| Workflow name | `release.yml` |
| Environment name | `pypi` |

**GitHub.** In the repository's *Settings → Environments*, create an
environment named `pypi`. Adding yourself as a required reviewer there makes
every release wait for a final click before it uploads, and a deployment tag
rule of `v*` limits the environment to release tags.

## Making a release

1. Update `__version__` in `src/engmech/__init__.py` (the package version is
   read from there) and merge that change to `main` with the rest of the
   release through a pull request, as usual.

2. Tag the merge commit on `main` and push the tag:

   ```bash
   git switch main && git pull
   git tag -a v0.4.0 -m "engmech 0.4.0"
   git push origin v0.4.0
   ```

3. Watch the run under *Actions → release*, and approve the `pypi`
   deployment if the environment requires it.

4. Check the result from a clean environment:

   ```bash
   uvx engmech --version
   uvx engmech validate
   ```

Tags such as `v0.5.0rc1` are marked as pre-releases on GitHub; pip only
installs them when asked (`pip install --pre engmech`).

## If something fails

- **Before the publish job**: nothing has been uploaded. Fix the problem on
  `main`, then move the tag to the fixed commit and push it again
  (`git tag -d v0.4.0 && git push origin :v0.4.0`, then tag and push as
  above).
- **After the publish job**: PyPI never accepts the same version twice. If
  only the GitHub release step failed, re-run that job from the run's page.
  Otherwise fix forward with a new patch version.

## Release notes

Release notes are generated by GitHub from the titles of the pull requests
merged since the previous release, so give pull requests titles that read
well in a list of changes. There is no hand-maintained changelog.

## README screenshots

The report screenshots in `docs/images/` are generated. After changing the
report's layout, regenerate them and commit the result:

```bash
uv run --with pillow python scripts/make_screenshots.py
```

This needs Google Chrome or Chromium (set `CHROME` to its path if it is not
found); `pngquant`, if installed, makes the files smaller.
